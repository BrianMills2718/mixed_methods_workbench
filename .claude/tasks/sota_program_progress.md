## Acceptance Criteria

- [ ] Every capability family has a current target, owner, dependencies, measurable success/readout, incumbent baseline, verification artifact, and claim limit.
- [ ] Current-state claims are refreshed from the local workbench, producer repos, prior investigations, agent memory, and active coordination state.
- [ ] External SOTA is refreshed from primary/authoritative sources with URLs, access dates, uncertainty, and freshness triggers.
- [ ] The north star, goal map, capability graph, critical path, and risk-ordered release skeleton are understandable to a teammate without repo context.
- [ ] The next one or two documentation-safe slices have explicit acceptance evidence, failure modes, adversarial audit, cleanup, and concern-register triage.
- [ ] Evidence coverage is honestly graded before any new enforcement; each proposed hard gate has positive and negative controls designed first.
- [ ] No implementation or producer-repo mutation occurs without explicit authorization of a named capability/release slice and a passed pre-implementation gate.
- [ ] Every verified increment is committed, pushed, and leaves a clean lane.
- [ ] A final SOTA/beyond-SOTA claim, if ever made, is independently signed off against frozen incumbent baselines on named tasks/domains; unsupported areas remain explicit.

## Constraints

- Documentation-only authority is active.
- Producer repos remain read-only during this investigation.
- QC plus PT is multi-method qualitative, not mixed methods.
- Synthetic fixtures license at most C-grade shape claims.
- No universal “quality” or “SOTA” score; use method-, task-, and domain-specific evidence.
- Work uses an in-repo worktree until each verified documentation or
  implementation increment is merged and cleaned.
